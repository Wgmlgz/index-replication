ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ 
База данных – данные, связанные между собой, отношения которых явно 
выражены, при этом специально спроектированные для использования 
различными приложениями [1]. 
Облачный сервис – программное обеспечение прикладного назначения, 
запускаемое на удалённых вычислительных машинах и предоставляющее 
конечному пользователю интерфейс взаимодействия с использован ием веб -
технологий. 
Шардинг – метод разделения и хранения единого логического набора данных 
в виде множества баз данных. 
Репликация – механизм синхронизации содержимого нескольких копий 
объекта (например, содержимого базы данных). 
LZ4 и ZSTD – алгоритмы сжатия данных без потерь, ориентированны е на 
скорость сжатия и распаковки. 
RabbitMQ – брокер обмена сообщениями. 
Агрегация данных – процесс объединения различных строк из таблиц с 
помощью специальных функций, которые называются агрегаторами.

ВВЕДЕНИЕ 
Быстрый рост объема данных, генерируемых различными отраслями 
промышленности, и возрастающая сложность современных приложений 
подчеркивают важность разработки эффективных и производительных систем 
управления данными временных рядов. Временной ряд представляет собой 
последовательность значений, собранных за определенные промежутки 
времени и расположенных в хронологическом порядке [2], явля ется 
важнейшим компонентом во многих областях, таких как финансы, 
здравоохранение, машиностроение , исследование климата  и другие . 
Необходимость исследования сценариев использования и разработки систем 
управления данными временных рядов является актуальной, поскольку эти 
системы играют неотъемлемую роль в облегчении анализа, хранения и доступа 
к данным временных рядов в различных областях. 
В эпоху, когда принятие решений на основе данных становится все более 
распространенным, стала очевидной потребность в передовых аналитических 
платформах, способных эффективно обрабатывать и анализировать данные 
временных рядов. Такие платформы должны не только эффективно управлять 
данными, но и предоставлять аналитические возможности для извлечения 
ценных сведений и облегч ения процессов принятия решений.  Однако при 
сравнении у аналитических платформ их систем управления данными 
временных рядов важно учитывать такие факторы, как прием и хранение 
данных, производительность запросов, масштабируемость и аналитические 
возможности. Различные системы могут иметь разную степень поддержки 
этих функций в зависимости от их дизайна и вариантов использования.  В 
совокупности выявлена проблема, что не имеется единой системы управления

2.1.1 Сравнение времени загрузки и эффективности хранения 
Производительность загрузки данных является важнейшим аспектом 
любой системы управления данными временных рядов, поскольку она 
напрямую влияет на способность системы принимать и обрабатывать большие 
объемы данных. Каждая из рассматриваемой БД использует определенные 
алгоритмы и методы для оптимизации загрузки данных. 
Сжатие данных – еще один существенный фактор при выборе базы 
данных временных рядов, так как оно помогает снизить требования к 
хранению и затраты. 
ClickHouse использует столбцовый  формат хранения данных и 
применяет такие методы, как сжатие данных и компиляция "точно в срок" (JIT) 
для оптимизации производительности загрузки данных. Данная БД использует 
различные алгоритмы сжатия, такие как LZ4 и ZSTD, для достижения высокой 
степени сжатия. Также у нее есть поддержка а томарной записи, которая 
позволяет записывать данные атомарно, что гарантирует целостность данных 
при возможных сбоях.

InfluxDB 2  использует специальный протокол Line Protocol, который 
обеспечивает быструю и эффективную загрузку данных.   В частности, 
использование более точных значений времени (с точность до наносекунд) 
позволяет повысить производительность загрузки. Для оптимизации 
занимаемого пространства производится компрессия данных , в частности 
используется алгоритм  GZIP для сжатия данных. Также используется 
собственный механизм хранения данных в виде дерева слияния временных 
структур (TSM) для обеспечения эффективного сжатия данных.   
TimescaleDB использует преимущества существующих и проверенных 
методов хранения и индексирования PostgreSQL. Однако в TimescaleDB 
применяется новый подход к разделению данных, называемый 
пространственно-временным разделением, который сочетает горизонтальное 
разделение по временным интервалам и вертикальное разделение по 
пространству. 
По результатам исследования представленных в статье [ 12] можно 
сделать вывод, что TimescaleDB способна импортировать данные значительно 
быстрее чем InfluxDB 2 и ClickHouse. Медленный прием данных InfluxDB 2 
может быть связан с его файловой структур ой TSM и методом сжатия. 
InfluxDB 2 имеет наилучшую степень сжатия 83.73%, что на 10.95% больше, 
чем TimescaleDB. Механизм сжатия ClickHouse имеет относительно плохую 
производительность, поскольку степень сжатия приближается к 100%. Это 
может быть связано с тем, что данная БД не оптимизирует разделение и 
упорядочивание данных в соответствии с меткой времени 
 
2.1.2 Сравнение производительности запросов к данным

требуется на распаковку данных при выполнении запросов. Существует баланс

При получении сами данных из InfluxDB была выявлена проблема, что 
несколько метрик группируются в одно поле Field. Это значит, что для каждой 
метрики строится свой временной ряд (таблица результата). Если бы InfluxDB 
формировал JSON-файл без дополнительной  обработки, который 
возвращается обратно на клиентскую часть у нас, размер получался бы K × N 
метрик, где K – количество метрик, N – количество записей. Для уменьшения 
размера получаемого файла, перед отправкой происходит сбор всех метрик в 
единый объект временного ряда и только затем происходит отправка данных 
обратно. Тем самым было получено , что размер JSON-файла возвращаемого 
становится в K раз меньше.

3.1.3 Реализация мер безопасности 
Безопасность системы была обеспечена путем внедрения целого ряда 
мер. К ним относятся надежная аутентификация пользователей, контроль 
доступа, шифрование данных. Эти меры безопасности были настроены с 
использованием возмо жностей, предоставляемых фреймворком ASP.NET 
Core, на котором построена система. 
Аутентификация пользователей: в системе реализована надежная 
аутентификация пользователей с использованием фреймворка Identity, 
предоставляемого ASP.NET Core. Когда пользовате ль регистрируется или 
входит в систему, его учетные данные сверяются с данными пользователя, 
хранящимися в MariaDB. Пароли хранятся в хешированном формате через 
SHA256 для обеспечения их безопасности. 
Шифрование данных: для защиты конфиденциальных данных в системе 
реализовано шифрование данных при передаче. При передаче все соединения 
между клиентом и сервером шифруются с помощью SSL/TLS, что гарантирует, 
что любые данные, передаваемые по сети, не могут быть перехвачены и 
прочитаны неавторизованными лицами.

private List<TimeSeriesDataJsonEntity> 
CreateTimeSeriesDataJsonEntities(List<FluxTable> measurementsResult) 
{ 
    var timeseriesDataJsonEntities = new List<TimeSeriesDataJsonEntity>(); 
    foreach (var table in measurementsResult) 
    { 
        foreach (var record in table.Records) 
        { 
            var tags = record.Values 
                .Where(x => !x.Key.StartsWith('_') && x.Key != "result" && 
x.Key != "table") 
                .ToDictionary(x => x.Key, x => x.Value.ToString()); 
 
            var timestamp = record.GetTimeInDateTime().ToString(); 
 
            var timeseriesDataJsonEntity = timeseriesDataJsonEntities 
                .Find(td => td.Timestamp == timestamp && 
td.Tags.SequenceEqual<KeyValuePair<string, string>>(tags)); 
 
            if (timeseriesDataJsonEntity == null) 
            { 
                var fields = new Dictionary<string, object> { { 
record.GetField(), record.GetValue() } }; 
 
                timeseriesDataJsonEntities.Add(new TimeSeriesDataJsonEntity 
                { 
                    Timestamp = timestamp, 
                    Fields = fields, 
                    Tags = tags 
                }); 
            } 
            else 
            { 
                timeseriesDataJsonEntity.Fields[record.GetField()] = 
record.GetValue(); 
            } 
        } 
    } 
    return timeseriesDataJsonEntities; 
}

public async Task<(int columnsCount, int rowCount, HashSet<string> columns, 
Dictionary<string, HashSet<string>> tags)> UploadDataFromCsv(string 
measurementId, string bucketId, List<string> lines) 
{ 
    await DeleteMeasurementById(measurementId, bucketId); 
 
    string[] headers = lines[0].Split(','); 
    PointData[] influxRows = new PointData[lines.Count - 1]; 
     
    var columnsCount = headers.Length - 1; 
    var rowCount = lines.Count - 1; 
    var columns = new HashSet<string>(); 
    var tags = ExtractTags(headers); 
 
    for (int i = 1; i < lines.Count; i++) 
    { 
        influxRows[i - 1] = CreateRow(headers, lines[i], measurementId, 
tags); 
    } 
 
    await _influxClient.GetWriteApiAsync().WritePointsAsync(influxRows, 
bucketId, TimeSeriesSettings.InfluxOrgId); 
 
    return (columnsCount, rowCount, columns, tags); 
} 
 
private PointData CreateRow(string[] headers, string line, string 
measurementId, Dictionary<string, HashSet<string>> tags) 
{ 
    string[] rowValues = line.Split(','); 
    PointData row = PointData.Measurement(measurementId) 
        
.Timestamp(DateTime.FromFileTimeUtc(DateTime.Parse(rowValues[0]).ToFileTimeU
tc()), WritePrecision.Ns); 
 
    for (int j = 1; j < headers.Length; j++) 
    { 
        if (headers[j].StartsWith('_')) 
        { 
            row = row.Tag(headers[j].Substring(1), rowValues[j]); 
            tags[headers[j][1..]].Add(rowValues[j]); 
        } 
        else 
        { 
            row = row.Field(headers[j], Double.Parse(rowValues[j])); 
        } 
    } 
    return row; 
}
